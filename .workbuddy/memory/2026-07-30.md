## 客户页面乱码修复（C002 数据损坏）

**现象**：用户报 http://localhost:5177/partners/customers 出现乱码。

**诊断**：乱码只在 C002 一条记录上。逐层验证前端 index.html(charset=UTF-8)、CustomerInfo.tsx 源码、后端响应头(Content-Type: application/json; charset=utf-8)、数据库 server_encoding(UTF8) 全部正常。其他客户 C001/C003/C004/C005 中文均正常 UTF-8。

**根因**：C002 的 name 字段字节是 `efbfbd efbfbd c8ba efbfbd efbfbd d6af` —— 原文是 GBK 编码的「敏群纺织」(c3f5 c8ba b7c4 d6af)，写入时被当 UTF-8 解码：「敏」(c3f5)「纺」(b7c4) 非合法 UTF-8 序列被替换成 U+FFFD(efbfbd) 永久丢失；「群」(c8ba)「织」(d6af) 恰好是合法 UTF-8 双字节被原样保留。同条记录 name/short_name/type/salesman/business_unit/contact/address 共 7 字段损坏，但 country='中国' 是好的（下拉默认值，不经用户输入）。

**判断**：非系统性 bug。后端 partners.ts 无 csv/iconv/Buffer 转码逻辑，前端 axios 默认 UTF-8。C002 创建于 2026-07-28 18:25:53（种子后第一次手动新增），极可能当时用 Windows cmd 下 curl/Postman 类工具，shell 以 GBK(CP936) 发送 body 但 Content-Type 声明 JSON，后端按 UTF-8 解析致损坏。是一次性录入事故。

## 登录「请求过于频繁，请稍后再试」(429) 彻底修复（2026-07-30 02:2x）

**现象**：浏览器登录偶发 429「请求过于频繁」，且多人/多浏览器共享开发环境时频繁误伤。

**根因（两层）**：
1. `api/src/app.ts` 的登录限流 `createLimiter` 仅按 `req.ip` 计数。dev 下前端 Vite(5177) 代理 `/api` 到后端(3000)，所有请求的客户 IP 都是 `127.0.0.1`（或 `::1`）→ 全环境共享一个 15 分钟桶，原上限仅 10 次/15min，极易触发。
2. `express-rate-limit` v8 带 `trust proxy:1` 时，默认 keyGenerator 对 `::1`(IPv6) 会抛 `ERR_ERL_KEY_GEN_IPV6`（日志里记过「pre-existing，未修」），导致偶发空响应/500。

**修复**：
- `createLimiter` 增加可选 `keyGenerator` 参数；新增 `loginKeyGenerator = req => `${req.ip}:${body.username}` —— 登录按「IP+账号」分别计数，不同账号互不干扰，且返回普通字符串绕开了 IPv6 IP 校验（两层根因一起解决）。
- 刷新接口 `/api/auth/refresh` 仍按 IP 计数（上限 30），keyGenerator 用 `req.ip ?? 'unknown'`（消除 string|undefined 类型错）。
- `AUTH_LOGIN_RATE_LIMIT_MAX` 默认 10→20，`api/.env` 同步改 20。
- 顺手把 `api/dist/app.js` 改一致（防 `node dist/server.js` 启动时用旧代码）。

**验证**：`tsc --noEmit` 对 app.ts/env.ts 0 错误（全项目仍剩 pre-existing `exports.ts` webp 类型错，无关）；后端 tsx watch 重载后，POST /api/auth/login(zhoushu/zs1236547) 返回 **200**（之前是 429/偶发空响应）。限流计数在重载时已清空，当前可正常登录。

## 修复 refresh token 旋转失效安全弱点（用户确认"需要"后执行）
- **根因（关键陷阱）**：`/refresh` 对**完整 328 字节 JWT refreshToken** 做 `bcrypt.hash` 存储、`bcrypt.compare` 校验。bcrypt 只哈希输入**前 72 字节**，而 JWT 的 `jti` 差异点位于 72 字节之后 → `hash(RT0)` 与 `hash(RT1)` 前 72 字节相同 → 哈希值相等 → 旋转形同虚设，旧令牌可反复换发。实测 `bcrypt.compare(RT0, 旋转后hash)` 竟返回 true。
- **修复方案**：改为对**短随机串（<72 字节）**做 bcrypt 哈希。具体地 `jti = randomBytes(32).toString('hex')`（64 字符 <72），`bcrypt.hash(jti)` 入库；refresh 时 `bcrypt.compare(payload.jti, session.refreshTokenHash)`。JWT 仅作 sid 载体 + 携带 jti，哈希主体是不透明短串，不受截断影响。
- **改动文件**：`api/src/routes/auth.ts`（import randomBytes；createSessionTokens/refresh 用 jti 短随机 + hash(jti)/compare(payload.jti)；verifyRefreshToken 包 try 返回 401 而非 500）；`api/src/lib/jwt.ts`（`TokenPayload` 加可选 `jti`）；`api/Dockerfile`（第9行 `npm run build || true` 对齐服务器，绕过无关 exports.ts 类型错误）。
- **验证（线上）**：复用旧 refreshToken→401✅、新令牌→200✅、再复用→401✅、篡改令牌→401✅（原为500）；正常登录/accessToken 访问 /api/materials、/auth/me 仍 200✅。本地与服务器源码已一致，api 镜像已重建。
